# CU-03 — Ver resumen de empleado

## Descripción funcional

Al hacer clic sobre una fila del listado de empleados, el sistema navega a la ficha de resumen de ese empleado. Esta pantalla agrega tres dimensiones de análisis en una sola vista: carga de trabajo actual (`WorkloadService`), tareas en curso (`WIPService`) y productividad de los últimos 30 días (`ProductivityService`). El cálculo se realiza íntegramente en el backend y se devuelve como un único objeto `EmployeeSummaryResponse`.

La pantalla dispone de cuatro pestañas de tareas que se cargan **bajo demanda** al seleccionarlas, reutilizando el endpoint `GET /tasks/filter` de CU-08. Además, la pantalla ofrece navegación directa a la vista de tareas: cada nombre de tarea en cualquier tabla es un enlace a la ficha individual de la tarea (`/tareas/{id}`), y las tarjetas de «Asignadas hoy» y «Vencidas sin cerrar» navegan a la vista de tareas filtradas (`/tareas/filtro`) con los parámetros preconfigurados correspondientes.

## Qué puede hacer el usuario

### Panel de KPIs

| KPI | Origen | Descripción |
|---|---|---|
| **Tareas pendientes** | `quick_stats.pending_tasks` + `pending_hours` | Número de tareas abiertas asignadas y suma de horas restantes (`WorkloadService`). |
| **Vencidas sin cerrar** | `workload.pending_tasks` filtradas por `is_overdue` | Tareas abiertas cuya fecha límite ha pasado, calculadas en el frontend a partir de la lista detallada de tareas pendientes. |
| **WIP actual** | `wip.wip_count` + `wip.status` | Número de tareas en paralelo y clasificación: `optimo`, `aceptable` o `sobrecargado` (`WIPService`). |
| **Prod. últimos 30d** | `quick_stats.avg_productivity` + `completed_last_30_days` | Ratio `horas_planificadas / horas_reales × 100` sobre tareas cerradas en los últimos 30 días (`ProductivityService`). |

Adicionalmente, en la cabecera se muestra un **badge de estado de carga** con la clasificación del `WorkloadService`: `Sobrecargado`, `Normal` o `Subcargado` (valores reales devueltos por `_workload_status`). Este badge es independiente del WIP.

### Pestañas de tareas

Cada pestaña invoca `GET /tasks/filter` con los parámetros correspondientes al seleccionarse:

| Pestaña | Filtros enviados |
|---|---|
| **Pendientes** | `employee_id`, `status=pending` |
| **Completadas** | `employee_id`, `status=completed` |
| **Asignadas** | `employee_id` (sin `status`) |
| **Responsable** | `employee_id`, `responsable=true` |

Todas las pestañas incluyen un filtro opcional de rango de fechas (`date_from`, `date_to`) que se aplica sobre `date_deadline`. La pestaña «Asignadas» incorpora además un subfiltro local «Todas / Abiertas / Cerradas» que filtra los resultados en el frontend por el campo `is_closed`.

### Navegación a tareas

La pantalla permite al usuario navegar directamente a vistas del módulo de tareas:

| Elemento | Acción | Ruta de destino |
|---|---|---|
| **Nombre de tarea** (en cualquier pestaña) | Clic en el enlace de la tarea | `/tareas/{task_id}` — ficha individual de la tarea |
| **Tarjeta «Asignadas hoy»** | Clic en la tarjeta | `/tareas/filtro?status=pending&date_assign={hoy}&employee_id={id}` |
| **Tarjeta «Vencidas sin cerrar»** | Clic en la tarjeta | `/tareas/filtro?status=overdue&employee_id={id}` |

### Guardar snapshot

El botón **Guardar snapshot** guarda el estado actual del resumen del empleado en la colección `entity_snapshots` de MongoDB (CU-17), con `entity_type = "employee"` y `entity_id = employee_id`.

## Datos mostrados

| Campo | Descripción |
|---|---|
| **Nombre, cargo, departamento, email** | Datos básicos del empleado obtenidos al cargar la ficha. |
| **Coste/h** | Coste horario del empleado en euros. |

| **Horas pendientes** | Suma de horas restantes en las tareas abiertas del empleado. |

---

## Restricciones de acceso

- **Director:** puede acceder al resumen de cualquier empleado del sistema.
- **Responsable:** solo puede acceder si el `employee_id` está en `cu.employee_ids` (embebido en el JWT en el momento del login). Un intento de acceso fuera del ámbito devuelve un 403.
- La validación de ámbito se ejecuta dos veces: una en `GET /employees/{id}` (vía `EmployeeService.get_employee`) y otra en `GET /dashboards/summary/employee/{id}` (vía `DashboardService.get_employee_summary`), para impedir el acceso directo al endpoint de dashboard eludiendo la ficha de empleado.

### Capa de rutas

El frontend realiza dos peticiones independientes al cargar la ficha: primero los datos básicos del empleado y después el bloque de KPIs. Además, al seleccionar cada pestaña de tareas, se lanza una tercera petición al endpoint de filtrado de tareas. Los tres endpoints aplican el guard `require_manager_or_above`.

```python
# routes/employee.py — datos básicos del empleado
@router.get("/{employee_id}", response_model=EmployeeDetail)
def get_employee(employee_id: int,
                 db: Session     = Depends(get_db),
                 cu: CurrentUser = Depends(require_manager_or_above)):
    return EmployeeService(db).get_employee(cu, employee_id)

# routes/dashboards.py — KPIs agregados (workload + WIP + productividad)
@router.get("/summary/employee/{employee_id}")
def employee_summary(employee_id: int,
                     db: Session     = Depends(get_db),
                     cu: CurrentUser = Depends(require_manager_or_above)):
     return DashboardService(db).get_employee_summary(cu, employee_id)

# routes/task.py — filtrado de tareas (reutilizado por las pestañas)
@router.get("/filter")
def filter_tasks(
    status:      Optional[str]  = Query(None, pattern="^(pending|completed|overdue)$"),
    employee_id: Optional[int]  = Query(None),
    responsable: Optional[bool] = Query(None),
    date_from:   Optional[date] = Query(None),
    date_to:     Optional[date] = Query(None),
    sort_by:     str = Query("date_deadline"),
    sort_order:  str = Query("asc"),
    page:        int = Query(1, ge=1),
    page_size:   int = Query(50, ge=1, le=200),
    # ... otros parámetros opcionales (stage_id, project_id, department_id, search, etc.)
    db: Session     = Depends(get_db),
    cu: CurrentUser = Depends(require_manager_or_above),
):
    return TaskService(db).filter_tasks(cu, status=status, employee_id=employee_id,
                                        responsable=responsable, date_from=date_from,
                                        date_to=date_to, sort_by=sort_by,
                                        sort_order=sort_order, page=page,
                                        page_size=page_size)
```

### `DashboardService` — orquestación de KPIs

El método invoca los tres servicios de métricas secuencialmente y construye un único `EmployeeSummaryResponse`. La validación de scope se repite aquí intencionalmente para proteger el endpoint de dashboard si se accede directamente sin pasar por el endpoint de empleado.

```python
# services/dashboard_service.py
def get_employee_summary(self, cu, employee_id):
    verify_employee_exists(self.db, employee_id)
    verify_employee_scope(cu, employee_id)   # segunda barrera de scope

    wl   = WorkloadService(self.db).calculate(employee_id=employee_id, detailed=True)
    wip  = WIPService(self.db).calculate(employee_id=employee_id)
    prod = ProductivityService(self.db).calculate(
        employee_id=employee_id,
        date_from=date.today() - timedelta(days=30),   # ventana deslizante de 30 días
        date_to=date.today(),
    )

    return EmployeeSummaryResponse(
        employee_id=employee_id,
        workload=wl,
        wip=wip,
        productivity_last_30_days=prod,
        quick_stats=EmployeeQuickStats(
            workload_status=wl.status,                  # "normal" | "sobrecargado" | "subcargado"
            pending_hours=wl.pending_hours,
            pending_tasks=wl.total_pending_tasks,
            completed_last_30_days=wl.total_completed_tasks,
            wip_count=wip.wip_count,
            avg_productivity=prod.average_productivity,
        ),
    )
```

### `WorkloadService` — carga de trabajo

Convierte el `employee_id` en `user_id` (clave de la tabla `project_task`) y calcula el porcentaje de ocupación sumando las horas pendientes sobre la constante `WORKLOAD_REFERENCE_HOURS`. Si el empleado no tiene `user_id` asociado, devuelve un objeto vacío en lugar de error.

```python
# services/metrics/workload.py
def _workload_status(percentage: float) -> str:
    if percentage > WORKLOAD_OVERLOADED_THRESHOLD: return "sobrecargado"
    if percentage < WORKLOAD_UNDERLOADED_THRESHOLD: return "subcargado"
    return "normal"

class WorkloadService:
    def calculate(self, employee_id: int, detailed: bool = False, root_only: bool = False):
        user_id = get_user_id_for_employee(self.db, employee_id)
        if not user_id:
            return self._empty(detailed)   # empleado sin cuenta de usuario en Odoo

        pending_rows   = get_assigned_open_tasks(self.db, user_id, root_only=root_only)
        cutoff         = date.today() - timedelta(days=COMPLETED_WINDOW_DAYS)
        completed_rows = get_assigned_closed_tasks(self.db, user_id, date_from=cutoff, root_only=root_only)

        pending_hours = sum(max(float(r.pending_hours or 0), 0) for r in pending_rows)
        workload_pct  = round((pending_hours / WORKLOAD_REFERENCE_HOURS) * 100, 2)

        result = WorkloadResponse(
            workload_percentage=workload_pct,
            pending_hours=round(pending_hours, 2),
            available_hours=float(WORKLOAD_REFERENCE_HOURS),
            status=_workload_status(workload_pct),
            total_pending_tasks=len(pending_rows),
            total_completed_tasks=len(completed_rows),
        )
        if detailed:
            # Solo se calculan las listas detalladas cuando las solicita el caller
            result.pending_tasks   = _format_pending(pending_rows)
            result.completed_tasks = _format_completed(completed_rows)
        return result
```

### `WIPService` — tareas en paralelo

Cuenta las tareas abiertas asignadas al `user_id` del empleado. La clasificación (`optimo` / `aceptable` / `sobrecargado`) usa dos umbrales configurables.

```python
# services/metrics/wip.py
def _wip_status(count):
    if count <= WIP_OPTIMAL_THRESHOLD:    return "optimo"
    if count <= WIP_ACCEPTABLE_THRESHOLD: return "aceptable"
    return "sobrecargado"

class WIPService:
    def calculate(self, employee_id: int, root_only: bool = False) -> WIPResponse:
        user_id = get_user_id_for_employee(self.db, employee_id)
        if not user_id:
            return WIPResponse(wip_count=0, status="optimo",
                               recommendation="Sin tareas asignadas")
        count = count_open_assigned_tasks(self.db, user_id, root_only)
        return WIPResponse(
            wip_count=count,
            status=_wip_status(count),
            recommendation=_recommendation(count),   # texto de consejo según el nivel
        )
```

### `ProductivityService` — productividad últimos 30 días

La fórmula `(planned / actual) × 100` se aplica sobre las tareas cerradas con imputación real. La reutilización de este servicio desde `DashboardService` (sin parámetros de proyecto) hace que la ventana temporal sea la única restricción activa.

```python
# services/metrics/productivity.py  (fragmento — lógica de cálculo)
for r in rows:
    if r.actual_hours > 0:
        pct = (r.planned_hours / r.actual_hours) * 100
        items.append(ProductivityTaskItem(productivity_pct=round(pct, 2), ...))
        total_pct += pct
        valid += 1

return ProductivityResponse(
    average_productivity=round(total_pct / valid, 2) if valid else 0,
    total_tasks=valid,
    tasks=sorted(items, key=lambda x: x.productivity_pct, reverse=True),
```

### `TaskService` — filtrado de tareas por empleado

Las pestañas de la ficha de empleado reutilizan el servicio de tareas de CU-08. El método `filter_tasks` aplica primero la lógica de scope y después construye la query filtrada. Según la combinación de `status` y `employee_id`, el servicio devuelve un schema de respuesta distinto optimizado para cada pestaña.

**Nota de diseño — scope en el contexto de la ficha de empleado:** cuando se proporciona `employee_id` (que es siempre el caso desde esta pantalla), el filtro de scope por proyectos (`cu.project_ids`) **no se activa**. La única barrera es que el `employee_id` esté en `cu.employee_ids`; si lo está, el Responsable ve **todas las tareas del empleado**, incluidas las que pertenezcan a proyectos fuera de su ámbito. Esta decisión es intencionada: un responsable necesita visibilidad completa de la carga de trabajo de su equipo para poder gestionarlo correctamente, aunque parte de esa carga provenga de otros proyectos. El filtro por `cu.project_ids` solo se aplica cuando `employee_id` es `None` (listado general de tareas, CU-08).

```python
# services/task_service.py
class TaskService:
    def filter_tasks(self, cu, status=None, employee_id=None,
                     responsable=None, date_from=None, date_to=None, **kwargs):
        # ── Scope: Responsable solo accede a sus empleados ──
        if employee_id is not None:
            verify_employee_exists(self.db, employee_id)
            if cu.is_responsable and employee_id not in cu.employee_ids:
                raise HTTPException(status_code=403, detail="Acceso denegado al empleado")

        query = build_filtered_query(self.db, status=status, employee_id=employee_id,
                                     responsable=responsable, date_from=date_from,
                                     date_to=date_to, **kwargs)
        result = paginate(query, page, page_size)
        hours_map = get_worked_hours_batch(self.db, [t.id for t in result["items"]])
        items = self._build_items(result["items"], status, employee_id, responsable, hours_map)
        return PaginatedResponse(items=items, total=result["total"], ...)

    def _build_items(self, tasks, status, employee_id, responsable, hours_map):
        """Selecciona el schema de respuesta según la pestaña activa."""
        use_pending   = status == "pending"   and employee_id is not None
        use_completed = status == "completed" and employee_id is not None
        use_assigned  = employee_id is not None and status not in ("pending", "completed")
        for task in tasks:
            if use_pending:    yield PendingTaskItem(...)   # worked_hours, pending_hours, is_overdue
            elif use_completed: yield CompletedTaskItem(...) # actual_hours, productivity, on_time
            elif use_assigned or responsable:
                                yield AssignedTaskItem(...)  # all hours, is_closed, is_overdue
            else:               yield TaskResponse(...)      # esquema genérico
```

| Pestaña del frontend | Parámetros enviados | Schema de respuesta |
|---|---|---|
| **Pendientes** | `employee_id`, `status=pending` | `PendingTaskItem` — incluye `worked_hours`, `pending_hours`, `is_overdue` |
| **Completadas** | `employee_id`, `status=completed` | `CompletedTaskItem` — incluye `actual_hours`, `productivity`, `completion_date`, `on_time` |
| **Asignadas** | `employee_id` (sin `status`) | `AssignedTaskItem` — incluye todas las horas, `is_closed`, `is_overdue` |
| **Responsable** | `employee_id`, `responsable=true` | `AssignedTaskItem` — mismo schema, filtrado por `responsable_id` |

### Capa de repositorio — `repositories/employee.py`

La consulta base usa `outerjoin` con `Department` para que los empleados sin departamento asignado no queden excluidos del resultado.

```python
# repositories/employee.py
def _base_query(db: Session):
    return db.query(*_base_columns()).outerjoin(
        Department, Employee.department_id == Department.id
    )

def get_employee_by_id(db: Session, employee_id: int):
    return (
        _base_query(db)
        .filter(Employee.id == employee_id, Employee.active == True)
        .first()   # None si no existe o está dado de baja
    )

def get_user_id_for_employee(db: Session, employee_id: int) -> Optional[int]:
    # Los servicios de métricas necesitan user_id (res_users) en vez de employee_id
    # porque project_task.user_ids referencia res_users, no hr_employee
    row = db.query(Employee.user_id).filter(Employee.id == employee_id).first()
    return row.user_id if row else None
```

### `build_filtered_query` — repositorio de tareas

El repositorio construye la query de forma dinámica aplicando filtros encadenados. Para el contexto de la ficha de empleado, los filtros relevantes son `employee_id` (join con `TaskAssignment` para buscar por asignación) o `responsable` (filtro directo por `Task.responsable_id`). El rango de fechas se aplica sobre `date_deadline`.

```python
# repositories/task.py
def build_filtered_query(db, *, employee_id=None, responsable=None,
                         status=None, date_from=None, date_to=None, **kwargs):
    query = db.query(Task).filter(Task.active == True)

    # Filtro por status → stage abierta/cerrada/vencida
    if status == "pending":
        query = query.filter(Task.stage_id.in_(open_stage_ids_subq(db)))
    elif status == "completed":
        query = query.filter(Task.stage_id.in_(closed_stage_ids_subq(db)))
    elif status == "overdue":
        query = query.filter(Task.stage_id.in_(open_stage_ids_subq(db)),
                             Task.date_deadline < date.today())

    # Filtro por empleado: asignación vs responsable
    if employee_id is not None:
        if responsable is True:
            query = query.filter(Task.responsable_id == employee_id)
        else:
            query = (query.join(TaskAssignment, Task.id == TaskAssignment.task_id)
                     .join(Employee, Employee.user_id == TaskAssignment.user_id)
                     .filter(Employee.id == employee_id))

    # Rango de fechas sobre date_deadline
    if date_from: query = query.filter(Task.date_deadline >= date_from)
    if date_to:   query = query.filter(Task.date_deadline <= date_to)

    return _apply_task_sort(query, sort_by, sort_order)
```
